# 操作系统研讨课Project 3 Design Review

## 1 实验目标

### 1.1 总体目标

Project 2已经实现了PCB、上下文切换、阻塞与唤醒、互斥锁、系统调用和定时器抢占。程序可以在用户态执行，但需要在内核启动时写死要运行的程序，不能通过命令动态管理进程。

Project 3计划在现有实现上增加Shell、进程创建与退出、同步与通信、双核调度和绑核功能，使用户可以通过终端实际操作系统。本设计覆盖Task1至Task5。本文中的P3功能为待实现的设计方案，不代表已经通过测试。

| 任务 | 主要目标 | 预期结果 |
|---|---|---|
| Task1 | Shell与进程管理 | 通过命令查看、创建和终止进程，并支持等待退出 |
| Task2 | Barrier、条件变量和Mailbox | 进程可以协调执行并交换数据 |
| Task3 | 双核启动与调度 | 两个核心可以同时执行用户进程 |
| Task4 | CPU亲和性 | 通过`taskset`指定进程允许运行的核心 |
| Task5 | 细粒度内核锁 | 两个核心访问不同内核资源时可以并行 |

课程要求中，S-Core完成Task1和Task2中的Barrier；A-Core完成Task1至Task3；C-Core完成全部任务，并在双核下通过全部测试。

### 1.2 与P2的主要区别

| P2现有实现 | P3计划扩展 |
|---|---|
| 启动时加载固定任务列表 | 启动Shell，之后通过`exec`创建任务 |
| 用户进程主要循环运行 | 用户进程可以正常退出，也可以被终止 |
| PCB主要记录调度状态 | PCB还记录等待退出的进程、资源和CPU亲和性 |
| 使用互斥锁保护临界区 | 增加Barrier、条件变量和Mailbox |
| 只有一个核心参与调度 | 两个核心分别执行和调度进程 |
| 单核下利用关中断保护内核操作 | 双核下还需要锁保护共享内核数据 |

## 3 Task1：Shell与进程管理

### 3.1 Shell的执行方式

Shell是用户态进程，启动后作为PID1运行。PID0仍用于表示内核启动或空闲执行流，不作为普通用户程序。Shell通过系统调用获取串口字符，本实验采用轮询方式，不要求实现串口中断输入。

Shell接收到字符后，将其放入有长度限制的输入缓冲区，并回显到终端。遇到回车后解析完整命令，遇到退格时同时修改缓冲区和屏幕。需要检查缓冲区上限，防止输入过长导致越界。

屏幕上半部分用于测试输出，下半部分用于Shell交互。换行、清屏和滚动要明确作用范围，避免Shell覆盖测试输出。未知命令显示`Unknown command`。

| 命令 | 处理方式 |
|---|---|
| `ps` | 显示PID、进程状态，双核阶段增加允许运行核心和当前运行核心 |
| `clear` | 清理终端显示，并恢复提示符 |
| `exec name args...` | 创建进程，并等待该进程退出 |
| `exec name args... &` | 创建进程，Shell立即继续接收命令 |
| `kill pid` | 终止指定进程 |
| `taskset mask name` | 按指定CPU掩码创建进程 |
| `taskset -p mask pid` | 修改已有进程的CPU掩码 |

`&`由Shell解析，不作为用户程序的普通参数。前台运行的含义是Shell调用`sys_waitpid`等待新进程，并不表示其他进程停止调度。

### 3.2 PCB与资源管理

P3框架已经增加`kernel_stack_base`、`user_stack_base`和`wait_list`。栈基址用于记录分配的页面，栈指针用于保存当前现场，两者不能混用。

| 字段或记录 | 作用 |
|---|---|
| `pid` | 标识进程，分配新进程时使用递增PID |
| `status` | 区分READY、RUNNING、BLOCKED和EXITED |
| `kernel_sp`、`user_sp` | 保存进程当前栈指针 |
| `kernel_stack_base`、`user_stack_base` | 回收或复用栈页面 |
| `list` | 连接进程当前所在的调度或阻塞队列 |
| `wait_list` | 保存等待本进程退出的其他进程 |
| 锁所有者记录 | 退出时找到并释放进程持有的互斥锁 |
| 阻塞原因或对象记录 | 终止阻塞进程时正确撤销等待关系 |
| `cpu_mask`、运行核心记录 | 限制调度核心，并显示双核运行状态 |
| 终止请求标记 | 通知另一核心上正在运行的进程退出 |

PCB槽位可以复用，但PID不直接等于数组下标。每次复用前要重置上下文、队列、等待关系、亲和性和P2工作量记录，防止新进程继承旧状态。

### 3.3 创建进程与参数传递

A/C-Core采用`sys_exec(char *name, int argc, char **argv)`。计划按以下步骤创建进程：

1. 验证程序名、参数数量和字符串长度，查找镜像中的程序信息。
2. 找到可用PCB，分配或复用用户栈和内核栈。
3. 加载程序，检查目标内存范围。
4. 将参数字符串复制到新进程用户栈，再建立`argv`指针数组，并补上`argv[argc]=NULL`。
5. 将用户栈指针调整为16字节对齐。
6. 初始化异常返回现场和`switch_to`现场，设置`sepc`、用户`sp`、`tp`、`sstatus`以及`a0=argc`、`a1=argv`。
7. 分配PID、设置默认时间片和继承的CPU掩码，最后加入就绪队列。

不能直接把Shell缓冲区的地址作为新进程长期使用的参数，因为Shell下一次输入会覆盖它。`crt0.S`清理BSS和调用`main`之前，也不能破坏传入的`a0`、`a1`。

S-Core接口通过寄存器直接传递有限数量的数值参数。实现时需要用`S_CORE`条件编译保证用户声明、封装、内核声明和测试程序使用同一种接口。

程序加载方面，当前Loader按镜像记录的固定入口复制代码。如果同一程序已有实例在运行，重新复制程序或清零其BSS可能影响旧实例。因此Task1先明确重复启动的限制；Task4需要在单独评估代码和可写数据布局后支持测试要求的共享代码实例。共享代码不等于共享栈，也不能默认认为多个实例的全局变量已经相互隔离。

### 3.4 退出、终止与等待

`sys_exit`结束当前进程；`sys_kill`结束指定进程；两者应复用统一的清理逻辑。`sys_waitpid`把调用者加入目标进程的`wait_list`，目标结束后唤醒全部等待者。

清理时需要处理：

1. 从就绪队列或对应阻塞队列移除目标，撤销其等待关系。
2. 释放持有的互斥锁。若采用P2的直接交接方式，还要更新被唤醒进程为新的锁所有者。
3. 唤醒等待目标退出的进程，使其返回原来的系统调用。
4. 将目标标记为EXITED，安排栈和PCB资源的回收。

当前进程退出时，CPU仍在使用它的内核栈，不能立刻把该栈分配给其他进程。计划采用延迟回收：先完成切换，再由安全的执行流回收旧栈和PCB。创建中途失败则立即撤销已分配资源，不能留下半初始化的就绪进程。

用户程序的`main`返回后，`crt0.S`必须调用`sys_exit`。现有的`ret`返回路径不能继续作为P3进程的正常结束方式。

## 4 Task2：同步与通信

### 4.1 Barrier

Barrier用于让一组进程在某个位置等待，直到本轮所有参与者都到达后再一起继续。

计划保存使用标记、key、目标人数、到达人数、本轮编号和等待队列。调用`wait`时增加到达人数；未达到目标时阻塞，最后到达的进程重置计数、进入下一轮并唤醒本轮全部等待者。

计数更新和进入等待队列必须在同一个受保护操作中完成。Barrier必须支持重复使用，不能只完成第一次同步。非法编号、无效目标人数和销毁时仍有等待者的情况都需要明确处理。

若参与者被终止，不能简单删除队列节点后假定原人数仍能到齐。计划将该轮标记为失效并解除等待，或拒绝继续使用该对象直到重新初始化；具体错误返回方式要与现有接口匹配。不能把提前唤醒误称为成功完成屏障。

### 4.2 条件变量

条件变量用于等待某个共享条件，例如“缓冲区中已经有数据”。条件本身由共享数据表示，条件变量保存等待队列，互斥锁保护条件检查。

`wait`需要把当前进程加入条件等待队列、释放互斥锁并阻塞。这几个动作必须协调完成，避免生产者已经发送通知，而消费者还没有入队，导致消费者永久等待。

被唤醒后，进程需要重新获取原互斥锁，再检查条件。用户侧使用`while`重新检查，而不是只检查一次，因为其他消费者可能先取走数据。

`signal`唤醒一个等待者，`broadcast`唤醒全部等待者。它们只表示条件可能发生变化，不保证等待条件一直成立，也不直接转移互斥锁的所有权。

### 4.3 Mailbox

Mailbox使用固定容量的FIFO字节缓冲区。框架给出的`MAX_MBOX_LENGTH`为64，计划采用环形缓冲区，记录读位置、写位置、已用字节数、名称、引用计数和等待队列。

| 操作 | 行为 |
|---|---|
| `open` | 按名称查找邮箱，存在则增加引用，不存在则创建 |
| `close` | 减少引用，最后一个引用关闭时处理等待者并回收邮箱 |
| `send` | 空间不足以容纳本次数据时阻塞，足够时完整写入 |
| `recv` | 数据不足以满足本次接收时阻塞，足够时完整读取 |

发送和接收都要检查长度。超过容量的请求不能进入永久等待。缓冲区内容和计数由同一把锁保护，阻塞时释放保护锁，恢复后重新检查条件。

写入后通知接收者，读取后通知发送者。由于不同进程可能等待不同长度的数据，计划广播通知并让等待者重新检查，避免只唤醒一个仍无法满足要求的进程而遗漏其他可运行者。

引用计数需要与实际打开关系一致，进程被终止时也要处理它持有的邮箱引用。不能在还有等待者或引用者时直接把邮箱槽位交给另一个名称使用。

## 5 Task3：双核启动与大内核锁

### 5.1 主核与从核初始化

双核共享内存，但各有自己的寄存器和执行流。启动时通过框架提供的核心编号获取方式区分两个核心；`mhartid`属于机器态CSR，不能默认认为S态内核可以直接读取它。

核心0负责一次性的全局初始化，包括BSS、任务信息、PCB池、同步对象和共享屏幕。另一核心使用独立启动栈，等待全局初始化完成，再设置自己的异常入口、当前运行状态和定时器。

从核不能再次清零BSS，否则会覆盖主核刚初始化的队列和锁。初始化完成标记需要配合内存同步，保证从核看到标记时，也能看到对应数据。按固件接口调用`send_ipi`唤醒另一核心，并按约定处理软件中断。

双核测试使用课程提供的`loadbootm`和SMP运行配置。启动参数还需要保留现有的任务数量、App Info位置以及核心编号，不能让它们占用同一参数而互相覆盖。

### 5.2 每核运行状态与调度

计划为每个核心保存自己的空闲PCB和当前运行进程，继续利用每核独立的`tp`寄存器指向本核PCB。当前进程不能作为一个由两个核心随意改写的普通全局指针。

初步采用共享就绪队列，由内核锁保护。调度器在持锁状态下选择符合本核亲和性的READY进程，将其移出队列并标记RUNNING，从而保证同一进程不会被两个核心同时选中。

若没有适合本核的任务，切换到本核空闲执行流，并允许中断继续唤醒系统。不能在持有内核锁时无限循环等待就绪队列，因为另一核心可能需要同一把锁才能唤醒进程。

### 5.3 大内核锁与上下文切换

Task3先采用一把大内核锁保护共享内核状态。进入异常或系统调用后获取锁，离开内核返回用户态前释放锁。获取和释放使用原子操作，并具备必要的内存顺序保证。

锁不能简单地在`switch_to`前释放，因为旧进程可能已经进入就绪队列，但旧栈上的切换尚未完成，此时另一核心可能错误地恢复它。

计划在共享状态更新和低层切换完成之前保持保护，并在新执行流的统一位置完成锁交接或释放。普通进程恢复、首次运行和空闲进程都必须经过一致的规则。锁保护的是内核操作阶段，不能在用户态持续持锁。

单核关中断只能阻止本核抢占，不能阻止另一核心访问共享数据。双核共享队列和锁状态必须使用跨核心同步。

## 6 Task4：CPU亲和性

计划为PCB增加`cpu_mask`。两核情况下，`0x1`表示只允许核心0，`0x2`表示只允许核心1，`0x3`表示两个核心都允许。

创建进程时默认继承父进程的掩码。Shell的`taskset mask name`在创建时设置掩码；`taskset -p mask pid`修改已有进程的掩码。需要验证掩码非零，并且不包含系统不存在的核心。

调度时按核心编号检查对应位是否为1。修改正在另一核心运行的进程时，不能只修改PCB后就声称迁移完成，需要通过重调度请求或后续中断使其离开不再允许的核心。`ps`分别显示允许掩码和实际运行核心，READY或BLOCKED进程不应被标为正在某核心运行。

`affinity`测试会创建多个同程序实例，要求共享代码、独立栈，并继承父进程的掩码。Loader和启动代码需要避免重复初始化破坏已有实例；P3尚未实现虚拟地址空间隔离，需要明确共享可写数据的影响。

## 7 Task5：细粒度内核锁

大内核锁会让两个核心的所有内核操作串行执行。Task5计划根据资源拆分锁，使一个核心处理屏幕时，另一个核心可以处理不相关的Mailbox或调度操作。

| 资源 | 计划保护内容 |
|---|---|
| PCB池与PID分配 | 创建、回收和PID分配 |
| 调度队列 | READY、BLOCKED、RUNNING之间的转换和选取 |
| 互斥锁对象 | 所有者、锁状态和等待队列 |
| Barrier或条件变量 | 计数、轮次和等待队列 |
| Mailbox | 环形缓冲区、引用关系和等待条件 |
| 屏幕 | 共享显示缓冲区和串口输出序列 |
| 内存分配器 | 栈页分配与回收 |
| Loader临时区 | 共用读盘缓冲区及程序加载过程 |

拆锁之后，进程退出、条件等待和Mailbox阻塞会同时涉及多个资源。因此需要规定锁顺序，并保证检查条件、加入等待队列和改变状态之间没有空隙。不能只删除大锁，再给每个函数随意加一把锁。

计划使用以下原则：

1. 普通资源锁不跨阻塞和调度持有，调度切换保护使用专门的交接规则。
2. 避免相反顺序获取同一组锁，持锁时避免再次调用会获取自身锁的函数。
3. 自旋锁保护区尽量短；检查状态后需要等待时，进入阻塞队列而不是长时间自旋。
4. 同时考虑本核中断与另一核心的访问，不能只依赖关中断。
5. 内核诊断输出也遵守锁规则，避免持屏幕锁时递归调用打印函数。

性能测试保留大锁和细粒度锁两个版本，保持CPU配置、时间片和打印频率一致。使用生产者、消费者统计消费速率，再加入`fly`比较干扰。指南要求细粒度锁版本加入飞机后，消费速度下降不能超过一半。

## 8 系统调用与寄存器

P3继续复用P2的系统调用通路：用户封装将参数写入寄存器，执行`ecall`，异常入口保存现场，内核按系统调用号分发，将结果写回保存现场，再恢复用户进程。

| 寄存器或上下文 | 在P3中的用途 |
|---|---|
| `a7` | 系统调用号 |
| `a0`至`a4` | 现有系统调用的参数；`a0`也接收返回值 |
| 新进程的`a0`、`a1` | A/C-Core启动时分别保存`argc`和`argv` |
| 用户`sp` | 指向独立用户栈，入口时保持16字节对齐 |
| `tp` | 指向本核正在运行的进程PCB |
| `sepc` | 异常返回地址，新进程初始化为程序入口 |
| `sstatus.SPP` | 新用户进程设为0，使`sret`返回U态 |
| `sstatus.SPIE` | 新用户进程设为1，使返回后具备中断使能状态 |
| `stvec` | 每个核心设置自己的S态异常入口配置 |
| `sie.STIE` | 使能S态定时器中断 |
| `sie.SSIE` | 双核阶段按框架需求使能软件中断 |
| `scause`、`stval` | 判断异常原因，记录诊断信息 |
| `regs_context_t` | 保存异常前的完整用户现场 |
| `switchto_context_t` | 保存内核切换所需的`ra`、`sp`和`s0`至`s11` |

新增服务需要同步修改系统调用号、用户头文件、用户封装、内核处理函数和`init_syscall`注册表。普通`ecall`处理完成后将`sepc`增加4，避免返回时再次执行同一条调用指令。

## 10 Design Review问题回答

### 10.1 创建、终止、等待和退出的伪代码

课件中的`spawn`对应本实验`exec`的创建行为，而不是直接跳转到另一个程序，也不是在此处实现完整的POSIX`exec`语义。

以下为流程伪代码。双核版的队列操作、状态转换和上下文切换还需要遵守前述锁规则。

```text
spawn/exec(name, argc, argv):
    检查程序和参数，预留PCB与栈资源
    加载程序，将参数复制到新用户栈
    初始化用户现场和内核切换现场
    设置PID、READY状态和CPU掩码
    原子地发布到就绪队列
    返回PID
    任一步失败时撤销已分配资源并返回失败

waitpid(pid):
    在保护下查找仍存活的目标
    若目标不存在或已经结束，按接口返回
    若目标是自己，返回失败
    将当前进程加入目标的退出等待队列
    设置BLOCKED并调度
    目标结束后被唤醒，返回等待结果

exit():
    清理当前进程的等待关系、锁和其他资源
    标记EXITED，唤醒退出等待者
    切换到其他进程，不再返回原用户现场
    在旧栈不再使用后回收栈和PCB

kill(pid):
    在保护下查找目标，检查是否允许终止
    若目标在另一核心运行，设置终止请求并请求其进入内核
    待目标停止使用现场后执行统一退出清理
    否则直接从所属队列移除并执行清理
    成功按接口返回1，无效目标返回0
```

`waitpid`中“判断目标存活”和“加入等待队列”必须连贯完成，否则目标可能在中间退出，导致等待者错过唤醒。实现时还需遵守课程约定：`exec`失败返回0；`waitpid`等待有效目标后返回目标PID，没有对应进程时返回0。

### 10.2 Kill持锁进程时需要处理什么？

需要记录锁的所有者，才能知道目标持有哪些锁。终止时遍历或使用持锁记录释放这些锁，有等待者时按既定规则交接并唤醒。目标如果正在等待别人的锁，还需要从对应阻塞队列撤销等待。

P2的锁没有完整所有者记录，需要在P3补充。直接交接锁时，即使原持有者被终止，也不能只唤醒等待者而忘记更新所有者。对于另一核心正在运行的进程，必须先让其停止执行，再释放其锁和栈，避免它继续访问已回收资源。

### 10.3 如何实现Barrier和条件变量？

Barrier使用到达计数和等待队列，最后一个参与者到达后重置本轮状态并唤醒全部等待者。轮次记录用于区分连续多轮同步。

条件变量使用等待队列，`wait`协调完成入队、释放互斥锁和阻塞；`signal`唤醒一个，`broadcast`唤醒全部。恢复执行后重新获取互斥锁，并用`while`重新判断共享条件。

两者的状态检查和队列更新都需要保护，不能把“检查条件”和“进入等待”拆成可被其他执行流穿过的两个步骤。

### 10.4 使用同步原语时遇到定时器中断怎么办？

用户进程持有互斥锁时可以被定时器抢占，锁不会因此自动释放。其他进程申请同一锁时应阻塞，持锁进程再次运行后继续执行并释放锁。

用户进程在Barrier或条件变量中阻塞后，不会被定时器自动解除等待；定时器可以调度其他READY进程，真正的唤醒由对应同步条件决定。睡眠队列则由时间到期唤醒。

修改内核中的同步状态时，需要保证操作一致性。进入S态陷入会清除本核的全局中断使能，但双核下另一核心仍能运行，因此还需要内核锁或对象锁保护。细粒度锁阶段还要保证中断处理不会在本核重复获取已经持有的锁。

### 10.5 如何保证Mailbox并发访问正确？

使用同一保护锁维护缓冲区内容、读写位置和已用长度。发送前检查剩余容量，接收前检查可读数据，不满足要求时进入对应等待队列并释放锁。唤醒后重新获取锁和检查条件，满足要求后再完整复制本次数据。

还需要保护邮箱的创建、名称查找、引用计数和销毁，确保一个进程关闭或退出时不会破坏其他进程正在使用的邮箱。

### 10.6 如何让主核和从核分别正常工作？

区分核心编号，为每核准备独立栈、当前PCB、异常设置和定时器。主核完成一次性的全局初始化，从核等待并确认这些结果可见后再参与调度。通过框架的IPI接口唤醒从核，避免从核重复清理BSS。

共享就绪队列的选取和RUNNING状态更新需要加锁，保证同一PCB不会同时运行在两个核心上。各核心无任务时进入自己的空闲执行流，不能占着共享锁等待任务出现。

### 10.7 C-Core的关键设计问题

CPU亲和性要同时约束创建、继承和调度，修改运行中进程的掩码还需要安排重新调度。多个同程序实例可以共享代码，但必须拥有独立PCB和栈，不能反复清零已有实例正在使用的数据。

细粒度锁要围绕资源及其操作关系设计，尤其关注队列转换、退出清理和阻塞时的锁交接。计划先保存可运行的大锁版本，再逐步拆分并比较相同负载下的性能，避免把降低打印频率带来的变化误认为拆锁收益。
